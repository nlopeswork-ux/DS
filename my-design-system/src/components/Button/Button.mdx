<h2 id="ux-guidelines" className="text-2xl font-semibold">UX Guidelines & When to Use</h2>

### ✅ When to use
- To trigger a concrete, immediate task — submit, save, confirm, create, continue.
- As the primary call to action of a form, modal, card or page section.
- Together with other hierarchies (Secondary, Tertiary, Link) to express the relative importance of several actions in the same area.

### 🚫 When not to use
- For simple navigation between pages, with no action to perform — use a `Link gray`/`Link color`, or a dedicated navigation component.
- To toggle a binary state (on/off) — use a `Toggle`.
- To pick one among several options — use `Radio` or `Dropdown`.
- For purely informational text with no associated action — it shouldn't be a button.

### Buttons should look like buttons

A button is an interactive element that results in an action described in it — one of the most essential components in UI design, so it's important to get it right. The most important rule when designing a button is that it should be **obvious** that it's a button. Users are already familiar with what buttons look like and how they behave; the more a button "looks like" a button, the easier it is to discover subconsciously — rectangles or rounded rectangles (including pill shapes) are always a safe choice.

As soon as a style strays too far from that container — an underline, an arrow with no container, plain text with no visual cue — buttons lose their actionable quality and users have to actively search for the action. This is exactly why `Link gray`/`Link color` are a deliberate exception: they intentionally borrow the hyperlink pattern for the lowest-priority actions, never a substitute for a real button that just "forgot" its container.

### Visual hierarchy

Without a clear hierarchy — visually and structurally — there's no visual cue, and the user is forced to read every label carefully to figure out which action matters. Reusing the same hierarchy for actions with different decision weight (e.g. several `Secondary gray` side by side with no `Primary`) creates exactly that friction.

### Destructive actions

There's a common notion that every "negative" or "destructive" action needs to be a big red button — in most cases that's not necessary, and it can make a screen look and feel busier than it needs to. When a destructive action is just one alternative among others (e.g. "Discard" next to "Save changes"), a plain `Secondary gray` already communicates the option clearly, without competing visually with the real primary action.

That said, when the destructive action **is** the primary action of the screen or modal (e.g. confirming "Delete" in a delete-confirmation dialog), flagging it with the `destructive` variant is the right call — it makes the consequence of that action unmistakable before the user commits to it.

<h2 id="anatomy-best-practices" className="text-2xl font-semibold">Anatomy & Best Practices</h2>

### Labels (button text)
- ✅ Always start with an action verb in the imperative: "Save changes", "Create account", "Invite member".
- ✅ Short and specific — ideally 1 to 4 words. Avoid generic phrases like "Click here" or a context-free "OK".
- 🚫 Don't write text in all caps — typographic weight and color already communicate priority.
- 🚫 Don't repeat information that's obvious from context ("Submit form" inside a form — "Submit" is enough).

### Icons (`iconLeading` / `iconTrailing`)
- **Left icon** reinforces the meaning of the action (e.g. "+" before "Add item"). It's the default position for semantic reinforcement icons.
- **Right icon** communicates navigation or progression (e.g. an arrow after "Continue", "See more →"). Use only when the action takes the user to a next step.
- 🚫 Avoid combining `iconLeading` and `iconTrailing` on the same button, except in very specific cases (e.g. bidirectional navigation actions) — too many icons dilutes focus on the text.
- Icons are always decorative (`aria-hidden`) — the button text is the only source of accessible meaning. An icon-only button needs an explicit `aria-label`.

See size and icon examples in the tab gallery under [UX Guidelines](#ux-guidelines).

### Optically balancing icons

Icons live on a 24px grid with a couple of pixels of padding between their "live area" and the frame — that extra padding throws a button with an icon slightly off-center, even though the numbers on paper (16px + 16px) look even. To counter this, `Button` shaves 2px off its nominal horizontal padding and wraps the text in a `px-0.5` frame that gives those 2px back — the total stays identical when there's no icon, and reads as centered once an icon is added (docs/components/buttons.md §1.4).

### Skeuomorphic style

Buttons use the composite `shadow-xs-skeuomorphic` token (drop-shadow + a darker inner-shadow along the bottom edge + a subtle inner-shadow border) instead of a flat `shadow-xs`, on every hierarchy with a visible fill or border (`Primary`, `Secondary gray`, `Secondary color`, and their `destructive` equivalents). It's a deliberately subtle effect — just enough depth for the button to read as slightly raised off the surface, without touching contrast or accessibility (`foundations/shadows-elevation.md §2`).

<h2 id="accessibility" className="text-2xl font-semibold">Accessibility (a11y)</h2>
- **Contrast:** every Button fill/text pair meets WCAG AA (ratio ≥ 4.5:1) in both Light and Dark Mode, through semantic tokens (`text-primary-on-brand`, `text-secondary`, etc. — `foundations/colors.md §2`).
- **Visible focus:** the focus ring (2px white halo + 4px color ring) must never be disabled — it's the primary visual cue for keyboard navigation.
- **Keyboard navigation:** Button renders a native `<button>` — reachable with `Tab`, activatable with `Enter`/`Space`, with no need for extra `tabIndex` or `role`.
- **Disabled state:** always uses the native `disabled` attribute, which automatically removes the button from tab order and communicates the state to screen readers — never simulate "disabled" with opacity/CSS alone.
