# Modal

A blocking dialog that interrupts the flow to confirm an action, collect short input or review information. Four sizes (`sm`, `md`, `lg`, `full`), responsive: `sm` and `md` become a bottom sheet on mobile, while `lg` and `full` become full screen.

<h2 id="ux-guidelines" className="text-2xl font-semibold">UX Guidelines & When to Use</h2>

### When to use
- **Simple action confirmation** — quick decisions with little content (`sm`, desktop and mobile).
- **Publication confirmation** — when a contextual featured icon helps validate status.
- **Short form** — `md`, with validation before completion and data preserved on error.
- **Settings editing** — `md` or `lg`, with clearly separated Save and Cancel and unsaved-change handling.
- **Information selection or review** — `lg`, using the body for lists, tables or summaries.
- **Extensive, focused task** — `full`; always check whether a dedicated page would fit better.
- **Destructive action** — compact composition with the consequences spelled out and direct labels such as "Delete item".

### When not to use
- Nested modals, excessively long forms, routine messages that fit in non-blocking feedback, and redundant confirmations for easily reversible actions.

<h2 id="anatomy-best-practices" className="text-2xl font-semibold">Anatomy & Best Practices</h2>

### Structure
- **Overlay** — `bg-overlay` at 70% with an 8px backdrop blur, on the modal z-index layer (`z-50`).
- **Header** — optional featured icon, title, supporting text and the close (X) button. Hidden icon on mobile for `md`/`lg`/`full`.
- **Body slot** — free content area (`md`, `lg`, `full`); scrolls when it overflows.
- **Footer** — optional start action (e.g. "Chat to us") and the action group. On mobile the actions stack with the primary action on top and the start action is hidden.

### Best practices
- Keep a clear hierarchy between header, body and footer; avoid visual clutter.
- The close button (X) and Cancel only *request* closure. If it would discard unsaved work, ask for confirmation first.
- For `md`/`lg`/`full`, a compact confirmation modal may open on top ("Discard changes", "Delete item") — a deliberate exception to the no-nesting rule. Keep the original modal and its data intact; only the confirmation is interactive.
- Esc and overlay clicks follow a risk-based policy (`dismissOnEsc`, `dismissOnOverlay`) and must never bypass a required confirmation.
- Prevent duplicate submissions with a loading state on the primary action; keep the modal open and show errors next to the fields.

<h2 id="accessibility" className="text-2xl font-semibold">Accessibility (a11y)</h2>
- **Semantics:** `role="dialog"` + `aria-modal="true"`, labelled by the title and described by the supporting text.
- **Focus:** the dialog receives focus on open, Tab/Shift+Tab are trapped inside, and focus returns to the trigger on close.
- **Scroll:** page scroll is locked while open.
- **Keyboard:** Esc requests closure (unless `dismissOnEsc` is off).
- **Close button:** icon-only, with an `aria-label` (default "Close").
- **Previews:** the `inline` prop renders in place for docs only — it skips the portal, scroll lock and focus trap, so don't use it in product code.

> Implementation note: the featured icon and close (X) button are internal placeholders until their own components exist.
